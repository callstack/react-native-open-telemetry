# React Native OpenTelemetry v0 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship the v0 vertical slice of `react-native-open-telemetry`: SDK set up on iOS, Android and web, JS spans exported through the native pipeline with correct nesting, all proven by an exact-output verification pipeline.

**Architecture:** JS spans live in stock `@opentelemetry/sdk-trace`; on end, one sync Nitro call hands each span (as a one-element array) to a Kotlin/Swift core that converts it off the JS thread to otel-java / opentelemetry-swift `SpanData` and exports OTLP. Context propagates through a runtime patch of `Promise.prototype.then` and timers. Web uses the upstream browser SDK with the same context manager. Every guarantee is a named scenario whose exporter output is compared exactly to a reviewed OTLP/JSON file and to a reviewed shape file.

**Tech Stack:** TypeScript, `@opentelemetry/api` 1.10, OTel JS 3.1.x (`sdk-trace`), `@opentelemetry/browser-sdk`, Nitro Modules 0.37.x, Kotlin + otel-java, Swift + opentelemetry-swift 2.6, Jest + `@react-native/babel-preset`, JUnit, XCTest, `e2e` 0.24.0 (agent-device / Playwright), Bun for scripts, GitHub Actions.

**Spec:** `docs/superpowers/specs/2026-11-10-rn-otel-design.md` (visual summary: https://claude.ai/artifact/UWTqogG1HpfZuQX2NHPQ12). Section references below (§n) point into the spec. Revised after the council review of 2026-11-21.

## Global Constraints

- RN New Architecture only, Hermes. Minimum RN **0.79** (OTel JS 3.x needs Metro ≥ 0.81.3); Nitro needs RN ≥ 0.75; Xcode ≥ 27.0 (opentelemetry-swift 2.6 dependencies need Swift 6.4); NDK ≥ 27.
- `@opentelemetry/api` 1.10; OTel JS stable 3.1.x / experimental 0.301.x; use `@opentelemetry/sdk-trace`, never `sdk-trace-base` / `sdk-trace-web`. Runtime code imports only the stable `@opentelemetry/semantic-conventions` entry; incubating keys are inlined.
- Native SDKs: otel-java (stable) directly, **not** opentelemetry-android; opentelemetry-swift 2.6 via SwiftPM (`spm_dependency` in the podspec).
- `react-native-nitro-modules` 0.37.x is a **peer** dependency with a pinned range.
- The Nitro spec uses only OTel-neutral shapes: no `io.opentelemetry.*`, no Swift OTel types, no callbacks or event emitters (`tsc` enforces the first two).
- Package `react-native-open-telemetry`; subpath `/metro`; entry function `startReactNativeSdk` on mobile and web, returning `{ tracerProvider, forceFlush, shutdown }`. No other public JS API in v0.
- The SDK never throws into the app: bad config, init failure or a missing native module → one `console.error` and a no-op handle.
- Times cross the seam as `HrTime` `[seconds, nanos]`. Numbers become OTLP `intValue` iff `Number.isInteger(v)` (same rule on JS, Kotlin, Swift).
- Custom names only under `com.callstack.*`; nothing under `otel.*`; semantic conventions first; `schemaUrl` set on tracers. SDK identity: `telemetry.distro.name` / `telemetry.distro.version`.
- Default sampler `ParentBased(AlwaysOn)` on both sides, honoring `traceFlags`.
- One resource, owned by native on mobile; JS adds no `telemetry.sdk.*`. The degraded flag is a scope attribute of the JS tracers.
- Endpoint: the OTLP/HTTP traces URL, used as given; same rule on Android, iOS and web.
- JS-thread work in `handOff` is marshalling and enqueueing only. Background flush never blocks the main thread (Android async; iOS inside a background task).
- Android native init runs only in the main process.
- Test mode is a **build flag**, never public API: JS `process.env.OTEL_TEST_MODE === '1'` inlined at bundle time; Android Gradle property `otelTestMode=true`; iOS `OTEL_TEST_MODE=1` at `pod install` (adds a Swift compilation condition). When on: JS IDs `0a…`, native IDs `0b…`, resource built from config only (no `telemetry.*`). Scenarios use explicit whole-µs timestamps from base **1767225600000000000 ns** (2026-01-01T00:00:00Z).
- Expected files: `verify/expected/<scenario>.shape.json` (hand-written, one per scenario) and `verify/expected/<scenario>.<platform>.otlp.json` (drafted with `--update`), platform ∈ `js | android | ios | web`, OTLP/JSON with hex IDs. `verify/` is behind `CODEOWNERS`. Any new or changed expected file needs the author's review before the task is done.
- Fixture JSON encodes `NaN`, `Infinity`, `-Infinity`, `-0` as `{"$num": "<name>"}`.
- `e2e` pinned to `0.24.0`; CI sets `E2E_TELEMETRY_DISABLED=1`.

## Review Focus

1. **Odd attribute values from JS** (`NaN`, `Infinity`, `-0`, integers above 2^53, empty arrays, mixed arrays after upstream sanitizing): the seam never crashes; values reach OTLP as upstream JS would encode them. Pinned by fixture `odd-attributes` (Tasks 8, 15, 18).
2. **Endpoint**: spans go to `url` exactly as given, on Android, iOS and web; no path is appended. Pinned in Tasks 16, 19, 21.
3. **App backgrounded right after work**: handed-off spans are exported without `flush()`; no main-thread block. Pinned by `background-flush` (Task 27).
4. **`startReactNativeSdk` called twice** (fast refresh re-runs `index.js`) or with config while native already initialized: second call returns the first handle with one warning; native config wins with one warning. Pinned in Task 14.
5. **Malformed `traceparent` passed to the native helper**: the span starts as a root, nothing throws. Pinned in Tasks 17 and 20.

export interface SeamSpanContext { traceId: string; spanId: string; traceFlags: number; traceState?: string }
export type AttrValue = string | number | boolean | string[] | number[] | boolean[];
export interface SeamAttribute { key: string; value: AttrValue }

export interface SeamLink { context: SeamSpanContext; attributes: SeamAttribute[] }
export interface SeamScope { name: string; version?: string; schemaUrl?: string; attributes: SeamAttribute[] }
export interface SeamSpan {

  start: HrTime; end: HrTime; attributes: SeamAttribute[]; events: SeamEvent[];
